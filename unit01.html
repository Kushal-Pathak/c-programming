Problem Analysis

Unit 1 · Problem Solving with Computer

Learning objectives

  • Define problem analysis and problem solving.
  • Identify input, processing, output and constraints.
  • Prepare a clear problem specification and check it with examples.

1. Definition

Problem solving is the process of identifying a problem and developing a systematic solution to achieve the required result. In computer programming, the solution is expressed as instructions that a computer can execute.

Problem analysis is the process of studying a problem to understand its requirements, inputs, processing, expected outputs and constraints before designing a solution. It answers what must be solved, not yet how to write the code.

2. Steps in computer-based problem solving

StepPurpose
Problem definition and analysisUnderstand the problem and requirements.
Solution designDevelop an algorithm and, if useful, a flowchart.
CodingTranslate the solution into a programming language.
Compilation and executionTranslate and run the program.
Testing and debuggingCheck actual results against expected results and fix faults.
Documentation and maintenanceRecord how the program works and improve it when required.

These steps may be repeated. Testing can reveal a missing requirement, so a programmer may return to analysis.

3. Input–Process–Output (IPO)

Input is data supplied to a program. Processing is the set of calculations or operations applied to the input. Output is the result produced after processing. A constraint is a rule or limit that the solution must satisfy.

ComponentExample: calculate the total and average of three marks
InputThree subject marks: 75, 80, 85.
ProcessTotal = m1 + m2 + m3; average = total / 3.
OutputTotal = 240; average = 80.
ConstraintsEach mark must be from 0 to 100; exactly three marks.

The IPO model helps separate data, calculation and result. A requirement describes what the program must do, such as displaying an error for an invalid mark.

4. Worked problem: electricity bill

A customer pays Rs. 10 per unit of electricity and a fixed charge of Rs. 50. Find the total bill for a given number of whole units.

Analysis elementSpecification
ProblemCalculate the final electricity bill.
InputNumber of units consumed.
ProcessingBill = units × 10 + 50.
OutputTotal bill in rupees.
ConstraintsUnits must be a non-negative whole number; fixed charge applies even at zero units.
Sample test25 units → Rs. 300; 0 units → Rs. 50.

A test case contains an input and its expected result. Planning test cases during analysis helps identify mistakes before coding.

5. Decomposition and abstraction

Decomposition means dividing a complex problem into smaller manageable parts. For a student result system, separate reading marks, validating marks, calculating the average and displaying the result.

Abstraction means focusing on essential details and ignoring unrelated details. To calculate average marks, the student’s home address is not required.

6. Common mistakes and exam focus

  • Do not start coding before understanding the required output.
  • Do not confuse input with output: radius is input; area is output.
  • Identify units, valid ranges and special cases (zero, negative or missing values).
  • State assumptions when the question does not provide every detail.
  • For an exam answer, define problem analysis, explain IPO, and give a worked example.

Algorithms
Unit 1 · Problem Solving with Computer
Learning objectives
  • Define an algorithm and its characteristics.
  • Write finite, unambiguous steps in academic format.
  • Use sequence, selection and repetition; dry-run a solution.
1. Definition
An algorithm is a finite sequence of well-defined, unambiguous and effective steps used to solve a problem or perform a computation. It accepts zero or more inputs, produces one or more outputs and terminates after a finite number of steps.
An algorithm is independent of a particular programming language. It can be written in simple English, pseudocode or represented by a flowchart.
2. Characteristics of a good algorithm
CharacteristicMeaning
InputAccepts zero or more clearly specified inputs.
OutputProduces at least one specified result.
DefinitenessEach step is precise and unambiguous.
FinitenessTerminates after a finite number of steps for valid inputs.
EffectivenessEvery step can be carried out in a finite amount of time.
CorrectnessProduces the required result for every valid input.
GeneralitySolves the stated class of problems, not just one example.
Efficiency is also desirable: a solution should use reasonable time and memory. Correctness comes first.
3. Rules for writing an algorithm
  • Write a meaningful title, input and output.
  • Begin with Start and finish with Stop in the common academic format.
  • Number the steps in logical order; use clear action words such as Read, Calculate, Display and Repeat.
  • Use ← for assignment and explicitly state the condition and update for a loop.
  • Initialize counters and accumulators before use.
  • Avoid language-specific syntax unless pseudocode is requested. There is no single mandatory numbering notation; consistency is important.
4. Three basic control structures
StructureMeaning and example
SequenceExecute steps one after another: read length, calculate area, display area.
SelectionChoose an alternative according to a condition: if marks ≥ 40, display Pass; otherwise display Fail.
IterationRepeat steps while a condition holds: add numbers from 1 to n.
5. Worked algorithm: area of rectangle
Input: length L and breadth B (positive numbers)
Output: area A
Step 1: Start.
Step 2: Read L and B.
Step 3: A ← L × B.
Step 4: Display A.
Step 5: Stop.
Example: L = 12, B = 5, output = 60 square units.
6. Worked algorithm: largest of two numbers
Input: a and b
Output: largest value
Step 1: Start.
Step 2: Read a and b.
Step 3: If a ≥ b, set largest ← a; otherwise set largest ← b.
Step 4: Display largest.
Step 5: Stop.
If both values are equal, either value is the largest. If the question asks to report equality separately, add a separate branch.
7. Worked algorithm: sum of first n positive even numbers
Input: positive integer n
Output: sum of first n positive even numbers
Step 1: Start.
Step 2: Read n.
Step 3: Initialize sum ← 0 and i ← 1.
Step 4: While i ≤ n, repeat Steps 5 and 6.
Step 5:     sum ← sum + 2 × i.
Step 6:     i ← i + 1.
Step 7: Display sum.
Step 8: Stop.
A counter records the current iteration; an accumulator stores a running total. A dry run is a manual execution of an algorithm using sample data to check each step.
Iteration and even numberRunning sum
Initial (i = 1)0
i = 1; 22
i = 2; 46
i = 3; 612
i = 4; 820
i = 5; 1030
i = 6; condition falseStop loop; output 30
The direct formula is n(n + 1). Both methods give 30 for n = 5. The loop demonstrates iteration; the formula needs fewer arithmetic operations.
8. Algorithm versus program
AlgorithmProgram
Language-independent solution steps.Instructions written in a programming language.
Designed before coding.Implementation of the solution.
Can be checked manually.Can be translated and executed by a computer.
Focuses on logic.Must follow language syntax and logic.
9. Advantages, limitations and common mistakes
  • Advantages: easy to understand, independent of language, useful for planning and detecting logical errors.
  • Limitations: lengthy for complex problems; does not execute by itself; no universal natural-language syntax.
  • Do not confuse first n even numbers with even numbers up to n. For n = 5, their sums are 30 and 6 respectively.
  • A loop without an update may not terminate. A counter initialized to the wrong value may skip or repeat an iteration.
  • In exams include Start, input, initialization, condition, update, output and Stop where relevant.

Flowcharts
Unit 1 · Problem Solving with Computer
Learning objectives
  • Define a flowchart and identify standard symbols.
  • Draw sequence, selection and iteration flowcharts.
  • Convert an algorithm into a flowchart and trace its paths.
1. Definition
A flowchart is a graphical representation of an algorithm or process using standard symbols connected by directed flow lines. It shows the sequence of operations, decisions, input, output and control flow of a solution.
2. Standard flowchart symbols
SymbolMeaning and use

Terminator (oval)		Start or end of the flowchart.

Process (rectangle)		Calculation, initialization or assignment.

Input/output (parallelogram)		Read input or display output.

Decision (diamond)		Tests a condition; outgoing branches usually labeled Yes/No or True/False.

Flow line (arrow)		Indicates the direction of control flow.

Connector (circle)		Connects separated parts of a flowchart on the same page.
Other symbols exist, such as the predefined-process symbol for a subroutine and the off-page connector. The six above are the main beginner symbols.
3. Rules for drawing flowcharts
  • Use a Start and a Stop terminator in a simple algorithm.
  • Use the correct symbol for each operation and arrows to show direction.
  • Write short, clear instructions inside symbols.
  • Label the outgoing paths of a decision; both paths must lead to the correct next action.
  • Prefer top-to-bottom or left-to-right flow; avoid unnecessary crossing lines.
  • For a loop, show initialization, condition, body, update and a return arrow.
  • Use matching connectors if lines would become confusing.
4. Sequence flowchart
Read length and breadth, calculate area and display the result. Each operation is performed once in order.
5. Decision flowchart
Read an integer n. The remainder when divided by 2 determines whether it is even or odd. A diamond has two outgoing paths here; both end at Stop.
6. Loop flowchart
The loop adds the first n positive even numbers. If the condition is true, add the next number and update i. The arrow returns to the condition. If false, display the sum and stop.
For n = 3, the true path executes three times and the false path once. The output is 12.
7. Algorithm versus flowchart
AlgorithmFlowchart
Written step-by-step solution.Graphical representation of solution steps.
Uses words, numbers or pseudocode.Uses standard shapes and flow lines.
Usually easier to edit as text.Often easier to visualize branches and loops.
Does not need drawing tools.Complex processes may require many symbols.
Language-independent.Language-independent.
8. Advantages, limitations and common mistakes
  • Advantages: clear visual logic, easier communication, supports debugging and program planning.
  • Limitations: drawing and modifying large flowcharts takes time; complex diagrams can become difficult to read.
  • Use a parallelogram for input/output, not a rectangle. Use a diamond for a condition.
  • Do not omit Yes/No labels, loop updates or arrows returning to the condition.
  • For exams, draw neat symbols, clear arrows and all branches, then trace a sample input.

History and Importance of C
Unit 1 · Problem Solving with Computer
Learning objectives
  • Explain the origin and evolution of C.
  • Describe the major features and uses of C.
  • Explain why learning C is useful and distinguish it from other language levels.
1. Definition
C is a general-purpose, procedural, statically typed programming language designed for efficient system and application programming. It supports structured programming, functions, direct memory access through pointers and portable source code.
2. History of C
C was developed by Dennis Ritchie at Bell Laboratories in the early 1970s, mainly in 1972, during the development of the UNIX operating system. C evolved from B, which was influenced by BCPL.
Year / periodDevelopment
1967BCPL, developed by Martin Richards.
Around 1969–1970B, developed by Ken Thompson, influenced by BCPL.
1969–1973 (especially 1972)Dennis Ritchie developed C at Bell Labs.
1973Much of UNIX was rewritten in C, demonstrating its usefulness for system programming.
1978Brian Kernighan and Dennis Ritchie published The C Programming Language (K&R C).
1989 / 1990ANSI C (C89) and ISO C (C90) standardized the language.
1999, 2011, 2018, 2024C99, C11, C17/C18 and C23 are later standard revisions; C23 was published in 2024.
Further reading: Dennis Ritchie: The Development of the C Language and C language history.
3. Features of C
FeatureExplanation
General-purposeUseful for many types of software.
Procedural / structuredPrograms can be divided into functions and use sequence, selection and iteration.
EfficientCompiled programs can use CPU and memory efficiently.
PortableStandard-conforming source code can be compiled on different platforms with appropriate tools.
Statically typedTypes are determined according to declarations and language rules.
Rich operators and standard libraryProvides many operations and useful library functions for input/output, strings and mathematics.
Memory accessPointers allow programmers to work with object addresses and memory.
Extensible / modularProgrammers can create reusable functions and libraries.
4. Why C is sometimes called a middle-level language
Many introductory textbooks describe C as a middle-level language because it combines high-level constructs such as functions and loops with low-level facilities such as pointers and bitwise operations. This is a teaching description, not an official language classification.
Low-level language (e.g. assembly)High-level language (e.g. C)
Closer to machine instructions.Uses more human-readable constructs.
Typically hardware-specific.Standard source can be portable.
More manual instruction-level work.Provides expressions, functions and control structures.
5. Applications and importance
  • Operating systems and kernels: system-level components.
  • Embedded systems and microcontrollers: small devices with limited resources.
  • Device drivers, networking libraries, databases and language runtimes.
  • Learning: builds understanding of data types, algorithms, memory, pointers and compilation.
  • C influenced the syntax and design of many later languages, including C++ and Java.
6. Advantages and limitations
AdvantagesLimitations
Efficient execution and memory control.Manual memory management requires care.
Portable source and wide compiler support.Hardware-specific code may not be portable.
Modular functions and extensive libraries.No built-in classes or automatic garbage collector.
Suitable for both system and application programming.No automatic array bounds checking; misuse can cause undefined behavior.
7. Common misconceptions and exam focus
  • C is not the first programming language.
  • C is a language; GCC and Clang are compiler tools.
  • C and C++ are separate languages.
  • Portability means source can be rebuilt on supported systems, not that every executable runs everywhere.
  • For an exam, name Dennis Ritchie, Bell Labs, around 1972, UNIX, and explain key features and uses.

Basic Structure of a C Program
Unit 1 · Problem Solving with Computer
Learning objectives
  • Identify the main sections of a C program.
  • Explain main, headers, declarations, statements and return.
  • Read and write a small complete C program.
1. Definition
The structure of a C program is the organization of source code into preprocessor directives, declarations, functions and statements according to the syntax rules of C. In a normal hosted C program, execution of user code begins in the main function.
2. A complete C program
#include <stdio.h>

int main(void)
{
    int length = 12;
    int breadth = 5;
    int area = length * breadth;

    printf("Area: %d\n", area);
    return 0;
}
Area: 60
Program elementExplanation
#include <stdio.h>Preprocessor directive that includes the standard input/output header, which declares printf and scanf.
int main(void)Defines the main function. int is its return type; void in the parameter list means no parameters.
{ }Curly braces enclose a block (function body).
int length = 12;Defines an integer variable and gives it an initial value.
int area = length * breadth;Multiplies the two values and initializes area.
printf("Area: %d\n", area);Calls a library function. %d displays an integer; \n represents newline.
return 0;Returns an integer status from main; zero indicates successful termination.
3. Traditional sections of a C program
Introductory textbooks often describe six sections. These are useful organizational conventions, not six compulsory sections. A small program may need only main and a header.
SectionPurpose and example
Documentation sectionComments describing purpose, author if required, or important assumptions.
Link section (header inclusion)Includes headers, e.g. #include <stdio.h>. The traditional name is not the same as the linker stage.
Definition sectionMacro definitions, e.g. #define LENGTH 12.
Global declaration sectionFile-scope declarations such as function prototypes or global variables.
main function sectionLocal declarations and executable statements inside main.
Subprogram sectionDefinitions of user-defined functions, e.g. calculateArea.
/* Calculate the area of a rectangle. */
#include <stdio.h>
#define LENGTH 12

int calculateArea(int length, int breadth);

int main(void)
{
    int breadth = 5;
    int area = calculateArea(LENGTH, breadth);
    printf("Area: %d\n", area);
    return 0;
}

int calculateArea(int length, int breadth)
{
    return length * breadth;
}
Area: 60
A function is a named block of code that performs a task. A function prototype declares a function’s return type and parameter types before its use. Here, calculateArea receives two integer values and returns their product. A function definition may also appear before main; separate sections are not mandatory.
4. General syntax and rules
  • C is case-sensitive: main and Main are different names.
  • Use a standard main definition: int main(void) or int main(int argc, char *argv[]) for hosted programs.
  • Most declarations and expression statements end with a semicolon; preprocessor directives normally do not.
  • Use matching braces and parentheses, and double quotes for ordinary strings.
  • Declare identifiers before referring to them where required.
  • Use meaningful indentation and names. Indentation helps readers but does not define C blocks.
5. Basic input and output
printf displays formatted output. scanf reads formatted input and stores converted values in variables. The address-of operator & tells scanf where to store a value. Check its return value to confirm that input was read successfully.
#include <stdio.h>

int main(void)
{
    int length, breadth;
    printf("Enter length and breadth: ");
    if (scanf("%d %d", &length, &breadth) != 2)
        return 1;
    if (length <= 0 || breadth <= 0 || length > 100 || breadth > 100)
        return 1;
    printf("Area: %d\n", length * breadth);
    return 0;
}
Example input: 12 5. Expected output after the prompt: Area: 60. The bounds keep the multiplication safe for C int ranges. These beginner scanf examples assume integer text within the representable int range; robust input parsing is studied later. The condition and operators will be studied in later units.
6. Common mistakes and exam focus
  • Do not write void main() in portable hosted C.
  • stdio.h is a header, not the executable library itself.
  • A declaration such as int area; is not the same as an assignment or a function call.
  • Avoid missing semicolons, unmatched braces and incorrect format specifiers.
  • In a diagram or written exam, explain the six textbook sections and show a complete example.

Coding, Compilation and Execution
Unit 1 · Problem Solving with Computer
Learning objectives
  • Explain coding, compilation, linking and execution.
  • Distinguish source, object and executable files.
  • Compile and run a C program using a terminal.
1. Definitions
Coding is the process of translating an algorithm or solution into instructions written in a programming language. The written program is called source code.
Compilation is the process of translating source code into a lower-level form, commonly machine or object code, while checking language rules. In everyday usage, compilation often refers to the entire build process including preprocessing, assembly and linking.
Execution is the process of running a program so that the computer performs its instructions and produces results.
2. Translation and execution stages
StagePurpose and typical result
Editing / codingWrite and save source code, e.g. area.c.
PreprocessingHandles directives such as #include and #define, expands macros and replaces comments with whitespace.
Compilation properTranslates preprocessed C into lower-level instructions, often assembly code (.s).
AssemblyConverts assembly into relocatable object code (.o).
LinkingCombines object files and required library references; resolves external symbols and produces an executable.
LoadingThe operating system prepares the executable and required libraries in memory.
ExecutionThe CPU carries out instructions; a hosted C program begins user execution at main.
Typical pipeline: source → preprocessing → compilation → assembly → linking → executable → loading and execution. Some implementations combine stages or use intermediate representations instead of writing each file to disk.
3. Source, object and executable code
File typeMeaning
Source file (.c)Human-readable C code.
Preprocessed file (.i)Expanded source after preprocessing.
Assembly file (.s)Low-level assembly instructions.
Object file (.o or .obj)Relocatable machine code and symbols, usually not directly runnable.
Executable (e.g. area or area.exe)Linked program that can be loaded and run on the target platform.
4. Worked example: compile and run
Save this program as area.c using a plain-text editor or an IDE. An IDE (Integrated Development Environment) combines editing and other programming tools, such as build and debugging tools.
#include <stdio.h>

int main(void)
{
    int length = 12;
    int breadth = 5;
    int area = length * breadth;

    printf("Area: %d\n", area);
    return 0;
}
Open a terminal in the folder containing area.c and use the commands for your operating system. See the setup notes below if you need to install a compiler.


Windows (Command Prompt or PowerShell)


gcc area.c -o area.exe
.\area.exe


macOS (Terminal)


gcc area.c -o area
./area


Linux (Terminal)


gcc area.c -o area
./area


The first command compiles and links the program. gcc starts the compiler, area.c is the C source file, and -o sets the name of the executable file. The file is named area.exe on Windows and area on macOS and Linux.


After the build succeeds, the second command executes the program from the current folder. It prints the following line.

Run gcc --version in the shell you plan to use. If it shows a compiler version, you can try the build command.


Optional compiler flags


For coursework, these options are recommended. They select C17 and help you catch common mistakes.


  • -std=c17 selects the C17 language standard.
    • 

  • -Wall enables a set of common warnings.
    • 

  • -Wextra enables additional warnings.
    •

gcc -std=c17 -Wall -Wextra -pedantic area.c -o area


5. Inspect separate stages (optional lab)


These commands use macOS or Linux syntax. If your system provides gcc instead of cc, use gcc in the build commands.


cc -E area.c -o area.i
cc -S area.i -o area.s
cc -c area.s -o area.o
cc area.o -o area
./area
-E stops after preprocessing; -S produces assembly; -c produces an object file without linking. The last compiler-driver command links the object file into an executable. See the GCC overall options documentation.

  • Saving area.c.txt instead of area.c can confuse tools.
  • Recompile after editing; running an old executable may show old results.
  • A successful build does not prove the logic is correct.
  • A linker error is different from a syntax error: it can occur when a referenced function definition is missing.
  • Do not memorize .exe as mandatory on every operating system.
  • For exams explain the stages and the difference between source, object and executable code.

Debugging and Testing
Unit 1 · Problem Solving with Computer
Learning objectives
  • Distinguish syntax, linker, runtime and logical errors.
  • Explain testing and debugging steps.
  • Design normal, boundary and invalid-input test cases.
1. Definitions
A bug is a defect or fault in a program that may cause incorrect or unexpected behavior. Testing is the process of executing or evaluating a program with planned test cases to detect defects and check whether it meets requirements. Debugging is the systematic process of identifying, locating, analyzing and correcting the causes of defects.
2. Types of programming errors
Error typeMeaning and example
Syntax errorViolation of language grammar, e.g. a missing semicolon.
Semantic / type errorViolation of language meaning or type constraints, e.g. assigning an incompatible pointer type without conversion. Some semantic mistakes are diagnosed, others are logical errors.
Linker errorA required definition is missing or conflicting, e.g. calling a declared function with no definition linked.
Runtime errorA problem during execution, e.g. failing to open a required file. Integer division by zero has undefined behavior and may crash; a crash is not guaranteed.
Logical errorThe program runs but gives a wrong result, e.g. using addition to calculate rectangle area.
3. Examples of errors and corrections
Syntax error:
int marks = 85
printf("%d", marks);
Correct: add a semicolon after 85.
int marks = 85;
printf("%d", marks);
Logical error:
int length = 12, breadth = 5;
int area = length + breadth;
Wrong result: 17. Correct expression: length * breadth, giving 60.
Runtime risk:
int divisor = 0;
/* Do not execute this division: 10 / divisor */
Check that divisor is nonzero before division. Do not assume that undefined behavior always causes a particular error message.
4. Testing methods
Testing methodPurpose
Unit testingTests an individual function or component.
Integration testingTests whether multiple components work together.
System testingTests the complete program against its requirements.
Black-box testingChecks inputs and outputs without depending on internal implementation.
White-box testingUses knowledge of code paths and conditions to design tests.
Regression testingRepeats relevant tests after changes to detect newly introduced defects.
These classifications describe different aspects of testing: a unit test may also be a black-box test. A dry run is a manual logic check, not actual program execution.
5. Test cases: pass or fail
Requirement: a student passes if marks are at least 40. Valid integer marks are 0 to 100 inclusive; invalid values must be reported.
InputExpected output and category
75Pass — normal case
25Fail — normal case
39Fail — just below boundary
40Pass — boundary
41Pass — just above boundary
0, 100 (separate cases)Fail, Pass — valid range boundaries
-1, 101 (separate cases)Invalid marks — invalid-input tests
A test case specifies input, expected output and relevant conditions. Run the program, compare actual and expected output, and mark Pass when they match or Fail when they differ. A program’s “Fail” output can be a passing test if that is the expected result.
6. Debugging process
  • Reproduce the problem using the failing input.
  • Identify expected and actual behavior.
  • Locate the likely cause using diagnostics, tracing, breakpoints or variable inspection.
  • Correct the defect, not only the symptom.
  • Rebuild and rerun the failing test; run related tests to detect regressions.
A debugger is a tool that allows controlled execution and inspection of program state. A breakpoint pauses execution at a selected location. Step execution runs one instruction or source-level step at a time; variable inspection shows current values. Common tools include GDB and LLDB.
7. Testing versus debugging
TestingDebugging
Detects defects and checks requirements.Locates and corrects the cause of a defect.
Uses test inputs and expected outputs.Uses diagnostics, tracing and inspection.
Can be done before or after fixes; tests may be planned early.Usually follows evidence of a defect.
Reports actual versus expected results.Produces a correction that must be retested.
8. Corrected program
#include <stdio.h>

int main(void)
{
    int marks;
    if (scanf("%d", &marks) != 1)
        return 1;
    if (marks < 0 || marks > 100)
        printf("Invalid marks\n");
    else if (marks >= 40)
        printf("Pass\n");
    else
        printf("Fail\n");
    return 0;
}
Example input: 40. Output: Pass. Test 39, 40 and 41 to check the exact boundary.
9. Common mistakes and exam focus
  • Do not test only one normal input; include boundary and invalid cases.
  • Compiler warnings are valuable even when the executable is produced.
  • Testing can reveal defects but generally cannot prove the absence of all defects.
  • Do not change the expected output just to make a failed test pass.
  • In exams explain the error types, testing/debugging differences and the steps with examples.

Program Documentation
Unit 1 · Problem Solving with Computer
Learning objectives
  • Define documentation and explain its importance.
  • Distinguish internal and external documentation.
  • Write simple, useful program documentation.
1. Definition
Program documentation is the written information that describes the purpose, design, operation, usage and maintenance of a software program. It helps users, developers and maintainers understand how to use, modify and test the program. Documentation should be created throughout development and updated when requirements or code change.
2. Types of documentation
Internal documentation is information included inside the source code, such as meaningful identifiers, comments and function descriptions. Meaningful naming and indentation also make source code self-explanatory.
/* Calculate simple interest using an annual rate in percent. */
double simpleInterest(double principal, double rate, double years)
{
    return principal * rate * years / 100.0;
}
External documentation is information stored outside source code, such as user manuals, design documents, algorithms, flowcharts, test reports and README files.
Internal documentationExternal documentation
Located within source code.Located outside source code.
Helps developers understand implementation.Helps users and developers understand usage, design and maintenance.
Examples: comments, meaningful names and function descriptions.Examples: README, user guide, design and test documents.
Updated when implementation changes.Updated when requirements, behavior or usage changes.
3. User and technical documentation
User documentationTechnical documentation
Explains how to install and use the program.Explains how the program is designed, built and maintained.
Intended for users.Intended for developers, testers and maintainers.
Examples: input instructions, sample outputs, troubleshooting.Examples: design, data definitions, algorithms, source and test reports.
A README may contain both user and technical information. The two categories are based on purpose and audience, not a strict file format.
4. Essential documentation contents
  • Title and purpose: what the program does.
  • Inputs, outputs, units, constraints and assumptions.
  • Algorithm or flowchart and main design decisions.
  • Build and execution instructions.
  • Examples, test cases and known limitations.
  • Maintenance notes and changes when needed.
5. Worked documentation example
The following is a short external document for a simple interest program.
Program: Simple Interest Calculator
Purpose: Calculate interest for a fixed annual rate.
Input: Principal (Rs.), rate (% per year), time (years).
Process: SI = P × R × T / 100.
Output: Simple interest in rupees.
Constraints: Non-negative inputs.
Example: 10000, 8, 2 → Rs. 1600.
Build: cc interest.c -o interest
Run: ./interest
Limitation: Does not calculate compound interest.
6. Comments and documentation
A comment is non-executable text inside source code used to explain purpose or logic. C supports block comments /* ... */ and, since C99, single-line comments // .... Comments are only one part of program documentation.
Poor commentUseful comment
// Add one to i before i++;// Move to the next student explains purpose.
// Set rate// Annual rate expressed as percent clarifies units.
Avoid comments that merely repeat obvious code. Update comments when code changes, and never include passwords or secrets in documentation.
7. Importance and common mistakes
  • Improves readability, maintainability and communication.
  • Helps users operate the program correctly.
  • Supports testing, debugging and future development.
  • Reduces dependence on the original programmer.
  • Do not write documentation only at the end or leave it outdated.
  • In exams define documentation, explain types, give examples and mention importance.
